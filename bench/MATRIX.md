# 共通ベンチマーク(同時取り込み × 分割 × 窓 × 精度)

複数の機種で、同じ条件・同じ手順で計測し、結果を比べられるようにするための決まりです。
計測する人(人または AI エージェント)は、この文書のとおりに実行し、決まりから外れた点があれば、結果の `notes` に必ず書いてください。

対象の機種(2026-11 時点):

| 機種の名前(`<machine>`) | GPU | 環境 | イメージ |
|---|---|---|---|
| `rtx3060` | NVIDIA RTX 3060 12GB | Ubuntu(Linux ネイティブ) | `:cuda` |
| `rx9060xt` | AMD RX 9060 XT 16GB | Windows 11 + Docker Desktop(WSL2、`/dev/dxg`) | `:rocm` |
| `colab-<GPU>`(例 `colab-a100`) | Google Colab の GPU(L4・A100 など) | Colab(Docker を使えない) | なし(イメージと同じ版の PyTorch・transformers・モデルを pip で入れる) |

## 1. 目的

次の問いに、実測の数値とグラフで答えます。

1. **同時に取り込むと、取り込みが終わるまでの時間は変わるか。**
   - 1 本の動画をそのまま取り込む場合と、同じ動画を 2・4・8 本に分けて同時に取り込む場合で、速さが変わるか
   - 合計 8 本の動画を、1 本ずつ・2 本同時・4 本同時・8 本同時で取り込んだとき、終わるまでの時間はどう変わるか
2. **窓の大きさ**(1・2・4・6 秒)によって、速さとベクトルの数がどう変わるか
3. **精度を下げると**(`DTYPE`・`IMAGE_MAX_SIDE`・`DIMS`、画像の上限トークン `IMAGE_MAX_TOKENS`)、どれだけ速くなり、品質がどれだけ下がるか

## 2. 用語

| 用語 | 意味 |
|---|---|
| 分割数 `k` | 合計 480 秒の映像を、何本のファイルに分けて取り込むか(1 / 2 / 4 / 8) |
| 同時数 `w` | サーバーの `INGEST_WORKERS`。同時に処理するファイルの数の上限(1 / 2 / 4 / 8) |
| 窓 `win` | `window_sec`。1 窓の枚数(`frames_per_window`)は窓の秒数と同じにする(1 秒に 1 枚)。重なりは 0、音声なし |
| セル | `(精度の条件, k, w, win)` の 1 つの組み合わせ |
| 完了時間 | セルの 1 回の計測で、**最初のジョブの `created_at` から、最後のジョブの `finished_at` まで**の秒数(サーバー側の時刻。`GET /api/jobs/{id}` の値) |

推論そのものは、`w` によらず 1 回ずつ順番に実行されます(`PriorityGate`)。`w` を増やして並ぶのは、復号・前処理・保存です。

## 3. 計測の組み合わせ

### 実験 1: 分割 × 同時数 × 窓(精度は既定)

- 精度: `DTYPE=bfloat16`、`IMAGE_MAX_SIDE=448`、`DIMS=768`(GPU の既定)
- `k` × `w` は、`k ≥ w` の 10 通りです(`k < w` は、ファイルの数より同時数が多いだけで意味がないため測りません)。

| | w=1 | w=2 | w=4 | w=8 |
|---|---|---|---|---|
| k=1(480 秒 × 1 本) | ○ | | | |
| k=2(240 秒 × 2 本) | ○ | ○ | | |
| k=4(120 秒 × 4 本) | ○ | ○ | ○ | |
| k=8(60 秒 × 8 本) | ○ | ○ | ○ | ○ |

  - k=8 の行が「8 本を 1 本ずつ・2・4・8 本同時」、対角(`k = w`)が「分けて全部同時」、w=1 の列が「分けただけの影響」です。
- 窓: 1 / 2 / 4 / 6 秒。各セルを **3 回**測り、中央値を使います。
- 計 10 × 4 × 3 = 120 回です。コンテナは `w` ごとに起動し直します(4 回)。

### 実験 2: 精度(27 通り)

- `DTYPE`: `bfloat16` / `float16` / `float32`
- `IMAGE_MAX_SIDE`: 448 / 336 / 224
- `DIMS`: 768 / 256 / 128
- 上の全組み合わせ(27 通り)ごとに、コンテナを起動し直して、次を行います。
  1. 取り込み: `k=8`、窓 2 秒、`w=1` と `w=4` を各 3 回(`w` を変えるため、条件ごとに起動は 2 回)
  2. 検索: 取り込みの後、`w=1` のコンテナで、文章の検索を並行 4・15 秒(`bench.py search` と同じ方法)を 1 回
  3. 品質: 4 章の評価セットをベクトルにし、基準との差と正解率を記録する
- 基準は `float32`・448・768 です。DIMS が小さい条件では、基準のベクトルを先頭から同じ次元に切り詰め、長さを 1 にそろえてから比べます。
- `float16` で NaN が出た場合や、起動に失敗した場合は、その条件を「失敗」として記録し、次の条件へ進みます(止めない)。

### 実験 3: 画像の上限トークン(2 通り)

- 精度は既定(`bfloat16`・448・768)のまま、`IMAGE_MAX_TOKENS` を 140 と 70 にして、実験 2 と同じ取り込み・検索・品質を測ります(既定の 280 は、実験 2 の既定の条件がそのまま比較の相手になります)。
- 足した理由: `IMAGE_MAX_SIDE` は、推論の前に画像を縮小するだけです。モデルのプロセッサが、画像を上限トークンに合わせて拡大・縮小し直すため、推論の量は変わりません(1080p の映像の 1 枚は、渡す大きさが 448・336・224 px のどれでも 264 トークンでした。2026-11-21 にイメージの中のプロセッサで確認)。推論の量を減らす設定は `IMAGE_MAX_TOKENS` です。
- モデルが受け付ける値は 70 / 140 / 280 / 560 / 1120 です。16:9 の映像の 1 枚は、140 で 120 トークン、70 で 66 トークンになります。
- コンテナの起動は 2 × 2 = 4 回です。2026-11-21 より前のスクリプトで計測を始めた場合は、`--experiments tokens --resume` で、この実験だけを後から足せます。

## 4. 素材

実在の映像は使いません。`bench/make_samples.py` で作る合成の素材だけを使います。

```bash
python bench/make_samples.py ./bench-media --split-set
```

| 素材 | 内容 |
|---|---|
| `split/k1/` 〜 `split/k8/` | 1080p・30fps・H.264(GOP 2 秒)・480 秒の元の動画 1 本を、1 / 2 / 4 / 8 本に分けたもの。分けたファイルは元の動画から同じ設定でエンコードし直して作るため、合計のフレームの数(14400)と中身は、どの `k` でも同じ |
| `quality/images/<448・336・224>/` | 品質の評価用の単色の画像 12 色。`IMAGE_MAX_SIDE` の条件ごとに、長辺をその大きさにしたもの(評価に使う `/compute/embed/images` は縮小しないため、送る側で縮小しておく)。単色のため、解像度(`IMAGE_MAX_SIDE`・`IMAGE_MAX_TOKENS`)による細部の失われ方は、この評価では分かりません。`DTYPE`・`DIMS` の差を見るためのものです |
| `quality/queries.json` | 各画像に対応する正解の文章(日本語と英語) |

素材は、機種ごとに作り直してかまいません(ffmpeg の版によりファイルは同一になりませんが、条件は同じです)。作るのに 5 分ほどかかります。

## 5. サーバーの起動

計測スクリプト(`bench/matrix.py`)が、条件ごとにコンテナを起動し直します。
機種ごとに違うのは、GPU を渡す引数(`--docker-args`)とイメージだけです。

| 機種 | `--image` | `--docker-args` |
|---|---|---|
| `rtx3060` | `ghcr.io/miyabiver39/embeddinggemma-poc:cuda` | `--gpus all` |
| `rx9060xt` | `ghcr.io/miyabiver39/embeddinggemma-poc:rocm` | `--device=/dev/dxg -v /usr/lib/wsl:/usr/lib/wsl:ro` |

- `rx9060xt` では、スクリプト・素材・結果のフォルダをすべて WSL2 の中(Linux 側のファイルシステム)に置き、WSL2 のシェルから実行します(`/dev/dxg` と `/usr/lib/wsl` は WSL2 の中にしかないため。Windows 側のフォルダは読み書きが遅く、計測に影響します)。
- スクリプトは、環境変数 `DTYPE` / `IMAGE_MAX_SIDE` / `DIMS` / `IMAGE_MAX_TOKENS` / `INGEST_WORKERS` を変えて起動し、`/healthz` が応答するまで待ちます。
- そのほかの設定は既定のままです(`EMBED_BATCH`・`TORCH_COMPILE`・`FFMPEG_HWACCEL` などを変えない)。
- `DATA_DIR` は `DIMS` ごとに分けます(DB が次元を記録して照合するため)。`TORCH_CACHE_DIR` は全条件で共通にし、compile をやり直さないようにします。置き場所は `--data-root`(既定は `<--out>/server`)です。
- 素材のフォルダは `/recordings` に読み取り専用でマウントします。コンテナは `127.0.0.1:18000`(`--port`)で待ち受け、名前は `mediasearch-matrix` です。
- 1 回の計測ごとに、取り込んだ取り込み元を削除してから次を測ります(DB が大きくなって速さが変わらないように)。

### Docker を使えない環境(Google Colab)

`--launcher process` を指定すると、コンテナの代わりに、その環境に入れた mediasearch を `uvicorn` で直接起動します。
環境変数と compile のキャッシュの置き場所は、イメージの起動スクリプト(`docker/entrypoint.sh`)と同じにそろえます。
手順は [matrix_colab.ipynb](matrix_colab.ipynb) にまとめています(Colab で開き、上から順に実行します)。

- 依存関係は、イメージと同じ版にそろえます(PyTorch 2.14.1 の CUDA 12.6 版、torchvision 0.29.1、transformers 5.23.0、モデルの版 `914f7f8`)。
- イメージの revision の代わりに、リポジトリのコミットと、PyTorch・transformers などの版を `machine.json` に記録します。
- 結果は Google ドライブに保存します。接続が切れた場合は、同じセルを実行し直すと続きから再開します。
- Colab の GPU は、ほかの利用者と同じ物理マシンを使うことがあり、値がばらつく可能性があります。3 回の値の幅(`completion_min` / `completion_max`)も確認してください。

## 6. 守ること

1. **イメージをそろえる。** 計測の前に `docker pull` し(Colab では、5 章の版で依存関係を入れ)、イメージの revision(ラベル `org.opencontainers.image.revision`)と digest を記録します。機種どうしで比べるときは、同じ revision から作られたイメージを使います。`INGEST_WORKERS` を含む版(fa80754 以降)が必要です。
2. **コンテナの自動更新を止める。** watchtower などの自動更新が動いていると、計測の途中でタグが新しいイメージに変わり、以後の条件が別のイメージで動きます(RTX 3060 の計測で起きました)。計測の間は止めるか、`--image` にタグではなく digest(`ghcr.io/...@sha256:...`)を指定してください。
3. **ほかの GPU の処理を止める。** 計測の前に、GPU を使うほかのコンテナ・アプリを止めます。止められないものがあれば `notes` に書きます。
4. **ウォームアップする。** コンテナを起動するたびに、窓の大きさごとに、測らない取り込みを 1 回行ってから計測します(初回は compile やカーネルの準備で遅くなるため)。
5. **3 回測って中央値を使う。** 外れた値も消さずに記録します。
6. **途中で止まったら、続きから再開する**(`--resume`)。最初からやり直す必要はありません。条件を変えて再開してはいけません。
7. **数値は推測で書かない。** 取れなかった値(例: WSL2 の AMD では GPU の使用率が取れない)は空のままにし、理由を `notes` に書きます。
8. 計測の途中で、計測に使うマシンの操作(ほかの重い処理)をしないでください。
9. **メモリに注意する。** サーバーは、同時数と窓の枚数が大きいほどメモリを使います。RTX 3060(メモリ 22GB のマシンで、ほかのサービスと同居)では、同時数 2 以上の条件(窓 2〜6 秒)で、マシン全体のメモリが尽き、カーネルがサーバーを止めました(計 9 回)。カーネルの記録では、止められたときのサーバーは、通常のメモリ(anon)が約 2.9〜4.2GiB、GPU への転送用の固定のメモリ(shmem)が約 2.6〜4.8GiB でした。コンテナにメモリの上限(`--memory 8g` / `12g`、スワップなし)を付けても、上限に達する前にマシン全体のメモリが尽きました(カーネルの記録は、すべて cgroup の上限ではなくマシン全体の不足 `CONSTRAINT_NONE`)。固定のメモリが上限の計算に入っていない可能性がありますが、確認していません。巻き込まれて、デスクトップの小さなプロセス(gnome-software など)も止められました。ほかのサービスが動くマシンでは、計測の前に空きのメモリ(`free -m` の available)を確かめ、12GB 以上空けてください。それでも止まった条件は失敗として記録され、次の条件へ進みます。上限を付けた場合や、止まった条件は `notes` に書きます。

## 7. 記録するもの

### 1 回ごとの記録(`results.jsonl`。1 行 1 回)

| 項目 | 内容 |
|---|---|
| `experiment` | `concurrency`(実験 1)/ `precision`(実験 2・3)/ `search` / `quality` |
| `dtype` / `image_max_side` / `dims` / `image_max_tokens` | 精度の条件(`image_max_tokens` が無い行は既定の 280) |
| `k` / `w` / `win` / `rep` | セルと、何回目か(ウォームアップは `rep = 0`) |
| `completion_sec` | 完了時間(2 章) |
| `windows` | 作られた窓の合計数 |
| `sec_per_window` / `realtime_factor` | 完了時間 ÷ 窓の数 / 480 ÷ 完了時間 |
| `jobs` | ジョブごとの `timings`(decode / embed / store などの内訳)と、`created_at`・`started_at`・`finished_at` |
| `infer_util` / `gpu_util` / `gpu_mem_max_mb` / `cpu_util` / `mem_max_mb` / `mem_total_max_mb` | 計測中の資源の使用状況(`/api/metrics` から。取れないものは null)。`mem_max_mb` はコンテナ全体のメモリ(ページキャッシュと固定のメモリを除く)の最大、`mem_total_max_mb` はコンテナ(cgroup)の使用量の最大で、ページキャッシュを含む(2026-11-21 より前のスクリプトでは記録されない) |
| `qps` / `latency_ms`(検索) | 件数/秒、p50 / p95 / p99 |
| `cos_mean` / `cos_min` / `nan` / `top1_acc` / `margin`(品質) | 基準との cos 類似度、NaN の有無、文章から画像を探した 1 位の正解率、正解と 2 位の点数の差 |
| `ok` / `error` | 成功したか、失敗の内容 |

### 機器の情報(`machine.json`)

機種の名前、GPU の名前とメモリ、ドライバの版、CPU の名前とコア数、メモリ、OS、Docker の版、イメージの revision と digest、計測の日時、`notes`(決まりから外れた点、気づいたこと)。

## 8. 実行の手順

Python は 3.10 以上が必要です(標準ライブラリだけで動きます)。環境によっては `python` を `python3` に読み替えてください。

```bash
# 1. 素材を作る
python bench/make_samples.py ./bench-media --split-set

# 2. 試しに少しだけ実行して、動くことを確かめる(k=1,2・w=1,2・窓 2 秒・1 回・精度は既定のみ。結果は別のフォルダ)
python bench/matrix.py --machine <machine> --image <image> --docker-args "<GPU の引数>" \
  --media ./bench-media --quick --out bench/results/matrix-quick

# 3. 本番(実験 1〜3)。時間がかかるので、バックグラウンドで実行する
python bench/matrix.py --machine <machine> --image <image> --docker-args "<GPU の引数>" \
  --media ./bench-media --out bench/results/matrix-<machine>

# 止まったら、同じコマンドに --resume を付けて再開する

# 4. 集計とグラフ(コミットする結果を作る)
python bench/matrix_report.py bench/results/matrix-<machine> --out bench/matrix-results/<machine>

# 2 台分がそろったら、比較のグラフも作る
python bench/matrix_report.py bench/results/matrix-rtx3060 bench/results/matrix-rx9060xt --out bench/matrix-results/compare
```

所要時間(RTX 3060 の実測): 実験 1 が約 1.3 時間(止まった条件を除く)、実験 2 が約 4 時間(うち `float32` の 9 条件が約 2.3 時間)、実験 3 が約 10 分です。コンテナの起動 1 回に 30〜50 秒かかります。

## 9. 結果の置き場所とコミット

- 1 回ごとの生のデータ(`bench/results/`)は、容量が大きいためコミットしません(`.gitignore` で除外済み)。
- `bench/matrix-results/<machine>/` に、次をコミットします。
  - `summary.csv` / `summary.json`(セルごとの中央値)
  - `results.jsonl`(1 回ごとの記録。資源の使用状況の時系列は含めない)
  - `machine.json`
  - グラフ(`*.svg`)と `report.html`
- 結果の要約(表と考察)は、`bench/README.md` の 5 章に機種ごとの節として追記します。`AGENTS.md` の 6 章「検証状況」には、確認できたことだけを追記します。
- コミットメッセージは日本語で、1 行目に要約を書きます(例: `docs: RX 9060 XT で同時取り込み・窓・精度の共通ベンチマークを計測`)。結果とドキュメントは 1 つのコミットにまとめてかまいません。スクリプトを直した場合は、別のコミットにします。
- main へは直接 push できません。ブランチを作り、プルリクエストで入れます。

## 10. 考察に書くこと

グラフと表から、少なくとも次に答えてください。答えられない場合は、その理由を書きます。

1. 分けて同時に取り込むと(対角 `k = w`)、1 本のまま取り込む(k=1)より何 % 速くなったか、あるいは遅くなったか
2. 8 本を 2・4・8 本同時にすると、1 本ずつより何 % 短くなったか。どこで頭打ちになったか
3. 頭打ちの原因はどこか(推論の稼働率、GPU の使用率、CPU、復号の時間の内訳から判断する)
4. 窓の大きさによって、1 秒の映像あたりの処理時間と、1 日あたりのベクトルの数・容量(1 窓約 3.2KB × DIMS/768 を目安)がどう変わるか
5. 精度の条件ごとの速さと品質。既定(bf16・448・768)と比べて、速くて品質が下がらない条件はあるか。`float16` で NaN が出たか
6. 画像の上限トークン(実験 3)を下げると、何 % 速くなったか
7. 同時数・窓の大きさと、サーバーのメモリ(`mem_max_mb`・`mem_total_max_mb`)の関係。失敗した条件があれば、その原因
